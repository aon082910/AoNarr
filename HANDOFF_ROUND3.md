## 1. What this work is

The maintainer gets mismatched media (wrong movie/show grabbed or imported). `MATCHING_ACCURACY_PLAN.md` (repo root) is the audit of every surface that matches a release or file to a library item, compared with how Sonarr/Radarr/Lidarr/Readarr do it, with ten design decisions the maintainer answered (section "Decisions (answered 2026-10-24)") and six ordered implementation rounds. **Read the plan first**, especially the Decisions section and the "Status: shipped" paragraphs under Rounds 1, 2 and 3. Round 4–6 sections are the remaining work.

Headline root cause, already fixed in principle: video types had no title check at grab time (`chooseBestResult` only name-checked non-tiered types), episode searches passed no identity, and import never re-verified the file against the target. Everything shipped so far is behind a per-type setting and **defaults to log-only** so nothing is rejected until the maintainer flips it.

### 3.1 Confirmed findings (fix all of these)

1. **Manual grab adds the download before the 409 check** — `server/src/routes/search.ts` grab route. `adapter.addDownload(...)` runs at ~line 297, the identity verdict and the new `HttpError(409, ...)` only after it (~313–323). A refused grab therefore leaves the release in qBittorrent/SABnzbd with no queue row, and the web "Grab it anyway" confirm (which re-posts with `force: true`) adds it a second time. Fix: move `parsedTitle = parseReleaseTitle(b.title ?? "")` and the whole verdict + 409 block to right after the blocklist check (~line 277), before client selection. Test: in `tests/searchRoute.test.ts`, the Round 3 409 test should also assert the download-client mock's `addDownload` was **not** called on the refused request and called once on the forced one (`getDownloadClientAdapter()` in the test returns the same mock instance the route gets).

2. **Music lead-artist rule kills the audiobook "main title" path** — `server/src/services/scheduler.ts` `releaseNameMatch` (~461–468). The new block requires the segment before the first ` - ` to name the whole title or the parent. Audiobook titles carry subtitles and releases lead with the main title only ("Sapiens - Yuval Noah Harari [M4B]", "Atomic Habits - James Clear (2018) [M4B]") → rejected. Fix: for `SUBTITLE_OPTIONAL_TYPES` let a lead whose every token belongs to the wanted title count as naming the title (`leadTokens.every(t => titleTokens.includes(t))`); keep the full-title requirement for `artist`. Add those two audiobook releases as positives in the existing scheduler tests.

3. **Lead-artist rule rejects artists whose spelling tokenizes differently and year-led names** — same block, ~466. `titleTokens("R.E.M.")` = r,e,m but releases write "REM"; "P!nk"/"Pink", "N.W.A"/"NWA", "Various Artists"/"VA"; and "1981 - Queen - Greatest Hits" has lead "1981". Fix: pick the lead as the first ` - ` segment that has a non-numeric token; compare the parent both token-wise and as a joined/initials form (`parentTokens.join("")`, first letters) against the lead's joined form; treat "VA" as naming "Various Artists". Add tests for REM, P!nk, VA, and the year-led release, and keep "ABBA - Greatest Hits" rejected for Queen.

4. **Bare-digit "later volume" rule fires on disc counts, bit depths, bitrates, ordinals** — `scheduler.ts` `namesLaterVolume` (~424). `titleTokens` splits letters from digits, so "2CD", "24bit", "96kHz", "64kbps", "20th Anniversary", "2nd Edition", "(10 Tracks)" right after the album/book title become a bare number and the release is rejected for every non-tiered type. Fix: the plan scoped this rule to ROM/`single`-shape types ("Super Mario Bros 3"). Thread `mediaType` into `releaseNamesTarget(releaseTitle, name, mediaType)` and pass a `bareNumberIsSequel` flag to `namesLaterVolume` that is true only for `mediaType === "rom"` (or `getMediaTypeConfig(mediaType).shape === "single"`). Also skip a digit whose following token is a unit (`cd|bit|khz|kbps|lp|tracks|th|nd|rd|st|disc`). Tests: "Artist - Album 2CD [FLAC]", "Artist - Album 24bit 96kHz", "Author - Book 2nd Edition" accepted; "Super Mario Bros. 3 (USA)" still rejected for "Super Mario Bros."

5. **Rematch keeps the WRONG previous title as a permanent alias** — `server/src/routes/media.ts` rematch (~1818–1821) and `server/src/services/releaseAliases.ts` `syncPrimaryTitle` (~102). Rematch exists to fix an item that Scan matched to the wrong provider entry, so the old title is usually another work's title ("Extraction 2" when the folder was "Extraction"). Storing it as an `original` alias makes the other film's releases match forever. Fix: `syncPrimaryTitle(id, { keepOldTitle = true })`: when false, DELETE the stale primary row instead of demoting it; the rematch route calls `syncPrimaryTitle(id, { keepOldTitle: false })` and stores the old title only when the request says so (add optional body field `keepOldTitleAsAlias: boolean`, default false; the web rematch dialog can offer a checkbox later). `backfillCleanTitles` should also pass `keepOldTitle: false`. The provider-refresh path in `libraryScan.ts` (`refreshOneMediaItem` first match: scan guess → provider title) keeps the default `true`, which is the case `original` was meant for. Update `tests/releaseAliases.test.ts` and `tests/mediaRoutesAliases.test.ts` (they currently codify the alias being kept).

6. **IRC single-item path lost the `parsed.year` guard** — `server/src/services/ircAnnounce.ts` (~79). The old loop rejected a tiered single item when `parsed.year` (first year anywhere) was more than one off `item.year`. `resolveReleaseItem` uses only `parsed.titleYear`, which is deliberately null when the year stands after the first quality word ("Dune.1080p.BluRay.x264.2021-GRP"), so a same-title film from another year is accepted. Fix: before `resolveReleaseItem`, pre-filter the tiered candidates with the old ±1 `parsed.year` guard **only when `parsed.titleYear` is null** (a title year found before the quality word keeps the gate's own check). Add an IRC test: movie "Dune" (1984) monitored, announce "Dune.1080p.BluRay.x264.2021-GRP" → no grab.

7. **IRC uses the containment rule for sports/ppv/course/adult/video although those types are capped at log** — `ircAnnounce.ts` (~79, ~121) treats `verdict.ok` as the match rule and never consults `identityModeFor`. For `CONTAINMENT_TYPES` the gate accepts any release whose title merely contains the item title ("UFC.300.Prelims" resolves to "UFC 300"), looser than the old `titlesMatch` equality. Fix: add an optional `strictTitle?: boolean` on `IdentityTarget`; `resolveReleaseItem` (or the IRC caller) sets it for containment types while `identityModeFor(type) !== "enforce"`, and `releaseIdentity.ts` skips the containment branch (~186) when it is set. Add an IRC test for ppv "UFC 300": "UFC.300.Prelims.720p.WEB-GRP" not grabbed, "UFC.300.PPV.1080p.WEB-GRP" grabbed.

## 4. How to work in this repo (learned the hard way)

- **Run tests from `server/`**: `cd server && npx vitest run <file>`. Running from the repo root picks up the web package's vitest v5 and fails spuriously. Full suite: `cd server && npx vitest run` (~10 min, `fileParallelism: false`, 165 files). Typecheck: `cd server && npx tsc --noEmit` and `cd web && npx tsc --noEmit -p tsconfig.json`.
- **Postgres tests**: CI runs them; locally `AONARR_DATABASE_DRIVER=postgres AONARR_DATABASE_URL=postgres://aonarr:aonarr@localhost:5432/aonarr npx vitest run <files>` against any Postgres 16 with a superuser `aonarr`/`aonarr` and database `aonarr`. SQL must work on both engines; `ON CONFLICT ... DO UPDATE SET x = excluded.x` is already used in both.
- **Schema changes** go in four places: `server/src/db/schema.sql`, `schema.postgres.sql`, `client.ts` (`ensureColumn` for SQLite upgrades) and `postgresSchema.ts` (ALTERs). `tests/dbMigrations.test.ts` has a legacy-schema regex that strips new columns; the last added was `grab_source TEXT`, and it uses `grab_source` as the sentinel column (`match_type` is also an FTS column, so it can't be the sentinel).
- **Corpus convention** (`tests/releaseCorpus.test.ts`, fixtures `tests/fixtures/release-corpus.jsonl` and `identity-library.json`): `expect` = today's behaviour; `todo.expect` runs via `it.fails` so it flips when a round fixes it; identity checks carry a `round` and run live for R1 and R3, R4 rows are `it.todo` until Round 4. `KNOWN_FUTURE_FIELDS` lists parser fields that don't exist yet (`rejected`, `seasonRange`).
- `chooseBestResult` return shape: tests use `toEqual({ result, quality })`, so only add the `identity` key when a verdict exists.
- Review workflows' verifier agents may leave scratch tests named `server/tests/zz_*.test.ts`; never commit those.

## Appendix: the 28 unverified review candidates

Each is a reviewer's claim from the first (interrupted) review run. Verify before fixing. Severities are the reviewer's.

1. **resolveReleaseItem in IRC is 'wanted-wide', not library-wide: an item that already has its file never makes the announce ambiguous**
   - Where: `server/src/services/ircAnnounce.ts:76` (reviewer severity: low)
   - Claim: The candidate lists are `media_items WHERE monitored = 1 AND has_file = 0` (line 76) and episodes `WHERE e.has_file = 0 AND e.monitored = 1` (lines 101-106), so the two-claimants ambiguity check the Round 3 design promises (Sonarr's MultipleSeriesFoundException, 'library-wide' in the module and function docstrings) only sees items still wanted. Concrete: 'Charmed' (1998) fully downloaded and 'Charmed' (2018) missing S01E01; announce 'Charmed.S01E01.720p.WEB-GRP' (no year) resolves `kind:'one'` to the reboot and is grabbed, where the same two items with both missing would be rejected as ambiguous (the existing resolveReleaseItem test asserts exactly that). Same for movies: 'Dune' (1984) on disk, 'Dune' (2021) missing, announce 'Dune.1080p.BluRay-GRP' goes to 2021.
   - Suggested fix: Resolve against every item of the relevant shape (all media_items / all shows), then apply the monitored/has_file filter to the single resolved item (and its episodes) before grabbing, so a complete same-title item still makes the announce ambiguous.

2. **An SxxEyy announce is resolved against single-shape movies before the episodic path**
   - Where: `server/src/services/releaseAliases.ts:159` (reviewer severity: low)
   - Claim: resolveReleaseItem judges only parsed.title/year/ids; it ignores release shape, and handleAnnounce runs it over single items first (ircAnnounce.ts:79) for every announce. Concrete: movie 'Dune' (1984) monitored and missing, announce 'Dune.S01E01.1080p.WEB.H264-GRP' resolves `kind:'one'` to the movie (verified) and tryGrabMatch grabs a TV episode as the film; the real target, a series 'Dune' with S01E01 missing, is never reached because the function returns after the first grab. The old loop had the same hole via guessTitleFromText, but the new resolver has `parsed` in hand and could have closed it.
   - Suggested fix: In handleAnnounce skip the single-shape resolution when parsed.seasonNumber != null, parsed.episodeNumbers?.length, parsed.absoluteEpisode != null, parsed.airDate or parsed.isFullSeason (a release shaped like an episode names no movie), or give resolveReleaseItem a shape filter.

3. **Music lead-artist rule: a lead containing the artist as a subset, or any separator other than ASCII ' - ', still passes another artist's album**
   - Where: `server/src/services/scheduler.ts:461` (reviewer severity: low)
   - Claim: The new rule only fires when `/ - /` (ASCII hyphen with spaces) occurs, and treats the lead as naming the artist when every parent token appears in it (`parentTokens.every(t => leadTokens.includes(t))`). Concrete, all for artist 'Queen', album 'Greatest Hits', verified via chooseBestResult: 'Queen Latifah - Greatest Hits (2003) [FLAC]' is chosen (lead 'queen latifah' ⊇ 'queen'); 'ABBA – Greatest Hits (1975) [FLAC]' (en dash), 'ABBA_-_Greatest_Hits_(1975)_[FLAC]' and 'ABBA-Greatest Hits (1975) [FLAC]' all skip the rule and are chosen, while only 'ABBA - Greatest Hits (1975) [FLAC]' is rejected. The plan states a leading artist-like segment that is NOT the parent must reject; these were accepted before Round 3 too, so this is an incomplete fix rather than a regression.
   - Suggested fix: Fold underscores and dashes like titleTokens/foldSymbols before testing for the separator (e.g. normalise `_` to space and `–—‐‑` to `-`, and accept `\s*-\s*` when the lead is clearly artist-like), and require the lead tokens to equal the parent tokens (or the parent plus stopwords) rather than merely include them.

If the JSON key is kept, re-read extra_metadata immediately before the write and apply the same COALESCE(external_ids,'') = ? guard the other writers use.

The other ~20 insert sites (import lists, Trakt/Plex sync, Overseerr, requests, scans) are plausibly meant to be covered by the nightly job, but the primary interactive add path is the one tha
   - Suggested fix: After the INSERT in /metadata/import, `await syncPrimaryTitle(Number(mediaItemId))` and start `refreshProviderAliases(Number(mediaItemId)).catch(() => undefined)` alongside the existing fire-and-forget matchAdditionalProviders, mirroring routes/media.ts:1553-1555.

6. **Library-wide Refresh can change an item's title without syncPrimaryTitle, leaving a stale 'primary' row that swallows a later user alias**
   - Where: `server/src/services/libraryScan.ts:1680` (reviewer severity: low)
   - Claim: refreshOneMediaItem (the per-item wrapper) now calls syncPrimaryTitle, but the type-wide Refresh job loops over refreshOneItem directly, and refreshOneItem rewrites media_items.title on a first match (line 2073, `title = ?, sort_title = ?` when newTitle and not alreadyMatched).    - Suggested fix: Call syncPrimaryTitle(item.id) inside refreshOneItem right after the UPDATE that can change title (or in the Refresh loop when result.ok), so every title writer keys the alias index; optionally make storeAliases promote a stale 'primary' row whose clean_title no longer equals the item's own instead of DO NOTHING.

7. **Duplicate merge cascade-deletes the loser's titles instead of carrying them to the keeper**
   - Where: `server/src/services/duplicateCheck.ts:271` (reviewer severity: low)
   - Claim: mergeMediaItems repoints REASSIGN_TABLES to the keeper and then deletes the loser (line 542); media_item_titles is not in that list, so the new ON DELETE CASCADE removes the loser's primary/original/provider/user alias rows. ## Decisions (answered 2026-10-24)

1. **Movie year tolerance: ±1**, the IRC path's current convention (`ircAnnounce.ts:79`). No `secondary_year` column.
2. **sports/ppv/course/adult/video: whole-word containment of the item title, in `log` mode** until a corpus of real announces shows the rule is safe. movie/series keep the exact/alias gate; anime deferred to Round 3 as planned.

6. **Alias backfill: a background job after the Round 3 migration**, one provider call per item through the existing Background Jobs widget, rate-limited. Refresh keeps aliases current afterwards.
7. **Anime numbering: AniList absolute first, TVDB/XEM fallback** when the release carries SxxEyy. `episodes.absolute_episode_number` is the stored source.

9. **`.iso`/`.img` single-file downloads: left for manual import** with reason `unsupported-extension`. Movie extensions unchanged.
10. **Scene numbering: scene-first precedence with aired fallback**, replacing the Round 195 OR, behind a `sceneNumberingMode=or` rollback setting.
